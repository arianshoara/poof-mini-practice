# POOF Mini Practice — AI Version Workflow

## پروتکل ثابت اجرای هر نسخه با کمک هوش مصنوعی

این سند مشخص می‌کند هر هوش مصنوعی در هر گفت‌وگوی تازه چگونه باید توسعه‌ی یک نسخه از پروژه را هدایت یا اجرا کند.

این پروتکل به شماره‌ی نسخه وابسته نیست. برای همه‌ی نسخه‌ها، از یک اصلاح کوچک تا یک Milestone معماری، ترتیب کلی ثابت است:

```text
Sync
→ Inspect
→ Define Version
→ Plan Small Steps
→ Implement One Step
→ Test
→ Commit
→ Repeat
→ Regression Test
→ Update Documentation
→ Merge
→ Tag
→ Release
```

هدف فقط رسیدن به کدی که ظاهراً کار می‌کند نیست. هر نسخه باید قابل توضیح، قابل آزمایش، قابل بازیابی و قابل ادامه‌دادن در یک گفت‌وگوی تازه باشد.

---

## 1. دستور شروع در یک صفحه‌ی تازه

برای شروع یک نسخه:

```text
POOF-SYNC: start version v0.x.0
```

مثال:

```text
POOF-SYNC: start version v0.6.0
```

برای ادامه‌ی نسخه‌ای که قبلاً شروع شده است:

```text
POOF-SYNC: continue current version
```

برای بستن نسخه و آماده‌سازی انتشار:

```text
POOF-SYNC: close version v0.x.0
```

فرستادن این دستور به‌تنهایی به معنی اجازه‌ی Push، Merge، Tag یا انتشار بیرونی نیست. هوش مصنوعی باید پیش از هر عملیات بیرونی، محدوده‌ی درخواست کاربر را بررسی کند.

---

## 2. دو حالت همکاری

### حالت راهنمایی‌شده

این حالت، روش پیش‌فرض پروژه است.

هوش مصنوعی:

1. یک قدم کوچک را توضیح می‌دهد.
2. فایل و محل دقیق تغییر را مشخص می‌کند.
3. کد دقیق همان قدم را ارائه می‌دهد.
4. روش آزمایش را می‌گوید.
5. منتظر نتیجه‌ی کاربر می‌ماند.
6. پس از موفقیت آزمایش، Commit همان قدم را می‌دهد.
7. سپس وارد قدم بعد می‌شود.

در این حالت نباید کل نسخه در یک پاسخ بزرگ ریخته شود.

### حالت اجرای مستقیم

فقط وقتی کاربر صریحاً از هوش مصنوعی می‌خواهد فایل‌ها را تغییر دهد.

هوش مصنوعی می‌تواند تغییرات را انجام دهد، اما همچنان باید:

- قدم‌ها را جدا نگه دارد؛
- قبل از ویرایش فایل موجود را بخواند؛
- تغییرات نامرتبط کاربر را حفظ کند؛
- پس از هر واحد منطقی آزمایش کند؛
- نتیجه و Commit پیشنهادی هر واحد را گزارش کند؛
- بدون اجازه‌ی روشن، Push، Merge، Tag یا Release انجام ندهد.

## 3. ترتیب منابع حقیقت

اگر میان گفت‌وگو، مستندات و کد تناقض وجود داشت، این ترتیب ملاک است:

1. وضعیت واقعی مخزن و فایل‌های کد
2. آخرین Tag و Release رسمی
3. شاخه‌ی فعال و Commitهای اخیر
4. قراردادهای داده و تصمیم‌های معماری
5. Roadmap و README
6. توضیحات گفت‌وگو

هوش مصنوعی نباید فقط با دیدن آخرین Tag نتیجه بگیرد نسخه‌ی بعدی هنوز شروع نشده است. ممکن است آخرین Release رسمی یک نسخه باشد، اما شاخه‌ی اصلی بخش زیادی از نسخه‌ی بعد را در خود داشته باشد.

در صورت تناقض باید آن را صریح گزارش کند:

```text
آخرین Release رسمی: v0.4.0
وضعیت شاخه‌ی اصلی: بخشی از v0.5.0 پیاده‌سازی شده است
نتیجه: ادامه‌ی v0.5.0، نه شروع دوباره‌ی آن
```

## 4. مرحله‌ی اجباری همگام‌سازی

هوش مصنوعی قبل از پیشنهاد اولین تغییر باید وضعیت واقعی پروژه را بررسی کند.

### 4.1 بررسی Git

در محیطی که Clone محلی وجود دارد، بررسی‌های پایه شامل این موارد است:

```bash
git status --short
git branch --show-current
git remote -v
git fetch --prune --tags origin
git log --oneline --decorate -10
git tag --sort=-v:refname
git rev-list --left-right --count HEAD...origin/main
```

قواعد:

- اگر Working Tree دارای تغییر است، نباید نادیده گرفته شود.
- تغییرات موجود ممکن است متعلق به کاربر باشند.
- روی Working Tree کثیف، Pull یا Merge خودکار انجام نمی‌شود.
- هیچ تغییر نامرتبطی Reset، حذف یا بازنویسی نمی‌شود.
- اگر دسترسی فقط به GitHub است، همین اطلاعات از شاخه‌ی اصلی، Commitها، Tagها و Releaseها استخراج می‌شود.

### 4.2 ساخت نقشه‌ی مخزن

ابتدا فهرست فایل‌ها تهیه می‌شود:

```bash
rg --files
```

در Repository کوچک، هوش مصنوعی باید تمام فایل‌های متنی پروژه را در اولین Sync بخواند.

در Repository بزرگ‌تر، باید حداقل این نقشه را بسازد:

- Entry Pointها
- صفحه‌ها یا Componentها
- فایل‌های Style
- Domain و Storage
- Data و Schema
- Testها
- Configuration
- Documentation
- Build و Deployment

ادعای «تسلط کامل» بدون خواندن کد فعلی پذیرفته نیست.

### 4.3 اسناد اجباری

در شروع هر گفت‌وگوی تازه، این فایل‌ها باید بررسی شوند:

```text
README.md
docs/ROADMAP.md
docs/AI_VERSION_WORKFLOW.md
docs/testing.md
docs/decisions.md
```

قراردادهای مرتبط نیز باید خوانده شوند. نمونه‌ی فعلی:

```text
docs/card-storage-contract.md
```

Roadmap عمومی فقط زمانی لازم است که تصمیم نسخه روی افق محصول اثر بگذارد:

```text
docs/PUBLIC_ROADMAP.md
```

### 4.4 خروجی اجباری Sync

اولین پاسخ باید این اطلاعات را بدهد:

```text
گزارش همگام‌سازی

- آخرین Release رسمی:
- Commit فعلی شاخه‌ی اصلی:
- شاخه‌ی فعال:
- وضعیت Working Tree:
- Milestone واقعی فعلی:
- بخش‌های کامل‌شده:
- بخش‌های ناتمام:
- اختلاف کد با README/Roadmap:
- کوچک‌ترین قدم بعدی:
```

تا این گزارش آماده نشده است، تغییر کد شروع نمی‌شود.

## 5. تعریف نسخه پیش از کدنویسی

پس از Sync، هوش مصنوعی باید برای نسخه یک Version Charter کوتاه بسازد.

### قالب Version Charter

```text
Version:
Milestone name:
User-visible outcome:
Learning objective:
Current starting point:
In scope:
Out of scope:
Dependencies:
Affected files/modules:
Data contracts affected:
Migration needed:
Main risks:
Test strategy:
Definition of Done:
Estimated implementation steps:
```

### پرسش‌هایی که باید پاسخ داده شوند

1. این نسخه دقیقاً چه مشکل واقعی را حل می‌کند؟
2. چرا الان باید ساخته شود؟
3. ورودی و خروجی Feature چیست؟
4. کدام Module مسئول آن است؟
5. کدام Module نباید مسئول آن باشد؟
6. آیا داده‌ی ذخیره‌شده تغییر می‌کند؟
7. آیا Migration یا Recovery لازم است؟
8. چه حالت‌های خطا و Edge Caseهایی وجود دارند؟
9. چگونه می‌فهمیم نسخه واقعاً کامل شده است؟
10. چه چیزی عمداً برای نسخه‌ی بعد باقی می‌ماند؟

اگر Scope مبهم باشد، کدنویسی نباید شروع شود.

---

## 6. تبدیل نسخه به قدم‌های کوچک

یک Milestone باید به چند واحد قابل آزمایش تقسیم شود.

هر قدم باید:

- فقط یک هدف منطقی داشته باشد؛
- مستقل قابل توضیح باشد؛
- تغییرات محدودی ایجاد کند؛
- روش آزمایش مشخص داشته باشد؛
- Commit مستقل و معنادار داشته باشد؛
- نسخه را واقعاً به Definition of Done نزدیک کند.

نمونه‌ی ساختار یک نسخه:

```text
Step 1 — inspect and close an existing architecture gap
Step 2 — implement the core behavior
Step 3 — connect the behavior to the real interface
Step 4 — cover states and edge cases
Step 5 — run end-to-end regression
Step 6 — update documentation
Step 7 — finalize release
```

تعداد قدم‌ها از قبل مقدس نیست. اگر بررسی کد نشان داد یک قدم بزرگ است، باید شکسته شود. اگر دو قدم مصنوعی و بسیار کوچک‌اند، می‌توانند در یک Commit منطقی ادغام شوند.

---

## 7. قالب اجباری هر قدم

پیش از ارائه یا اجرای تغییر، هوش مصنوعی باید هر قدم را با این قالب معرفی کند:

```text
STEP n / total — نام قدم

هدف:
چرا اکنون:
وضعیت فعلی کد:
فایل‌های درگیر:
مسئولیت هر فایل:
تغییر دقیق:
ارتباط با بخش‌های موجود:
چیزی که عمداً تغییر نمی‌کند:
ریسک‌ها:
روش آزمایش:
نتیجه‌ی مورد انتظار:
Commit پس از موفقیت:
```

### قواعد ارائه‌ی کد

- ابتدا فایل موجود خوانده می‌شود.
- محل دقیق درج یا جایگزینی مشخص می‌شود.
- کد باید با Naming و Style موجود سازگار باشد.
- از ساخت Function یا Abstraction بدون مصرف واقعی پرهیز می‌شود.
- اگر فقط چند خط تغییر می‌کند، Patch دقیق داده می‌شود.
- اگر جایگزینی کامل فایل ضروری است، کل فایل تازه با نام و مسیر روشن ارائه می‌شود.
- کد نسخه‌های آینده زودتر وارد نسخه‌ی فعال نمی‌شود.
- UI مستقیماً به Storage Key، SQL یا Provider خاص قفل نمی‌شود.

### توقف میان قدم‌ها

در حالت راهنمایی‌شده، پس از ارائه‌ی تست باید منتظر نتیجه‌ی کاربر ماند.

هوش مصنوعی نباید با فرض موفقیت تست، خودکار وارد قدم بعد شود.

---

## 8. چرخه‌ی ثابت هر قدم

هر قدم دقیقاً این چرخه را طی می‌کند:

### 8.1 Inspect

- خواندن فایل‌های مرتبط
- پیدا‌کردن Call Siteها و Dependencyها
- بررسی قرارداد داده
- بررسی تست‌های قبلی

### 8.2 Explain

- توضیح ساده‌ی مشکل
- دلیل انتخاب راه‌حل
- محل قرارگیری تغییر
- اثر آن بر Flow کامل

### 8.3 Implement

- انجام فقط همان تغییر
- پرهیز از Refactor نامرتبط
- حفظ سازگاری با داده‌ی قبلی

### 8.4 Verify

- اجرای تست همان Feature
- بررسی Console
- Refresh و Persistence در صورت ارتباط
- بررسی Regression نزدیک

### 8.5 Review Diff

```bash
git diff -- path/to/changed-file
git diff --check
```

### 8.6 Commit

فقط پس از موفقیت تست، تغییر همان قدم Commit می‌شود.

## 9. قانون Commitها

هر Commit باید یک تغییر منطقی و آزمایش‌شده را ثبت کند.

### Prefixهای پیشنهادی

```text
feat:
fix:
refactor:
test:
docs:
chore:
```

نمونه:

```text
refactor: use getCardById for card actions
feat: add card storage migration
test: document v0.6 recovery scenarios
docs: finalize v0.6.0 milestone
```

### قبل از Commit

```bash
git status --short
git diff -- path/to/changed-file
git add path/to/changed-file
git diff --cached
git commit -m "type: clear description"
git status --short
```

قواعد:

- فقط فایل‌های همان قدم Stage می‌شوند.
- تغییرات نامرتبط در Commit وارد نمی‌شوند.
- یک Commit نباید چند Feature نامرتبط داشته باشد.
- برای هر تغییر چندخطی کوچک، Commit مصنوعی جدا ساخته نمی‌شود.
- Commit قبل از تست ثبت نمی‌شود.
- هوش مصنوعی نباید ادعا کند Commit انجام شده، مگر اینکه Hash واقعی داشته باشد.

## 10. ماتریس تست مشترک

همه‌ی موارد برای همه‌ی Featureها اجباری نیستند. هوش مصنوعی باید موارد مرتبط را انتخاب و دلیل حذف موارد نامرتبط را روشن کند.

### رفتار اصلی

- Happy Path
- Empty State
- Invalid Input
- Error State
- Repeat Action
- Cancel/Back
- Refresh
- Navigation Away and Return

### ظاهر و دسترسی

- Mobile
- Desktop
- Classic
- Snowy
- Keyboard Navigation
- Focus State
- Reduced Motion در صورت ارتباط
- RTL/LTR در صورت ارتباط
- نبودن Scroll افقی ناخواسته

### داده و ذخیره‌سازی

- Create
- Read
- Update
- Delete
- Refresh بعد از هر عملیات مهم
- داده‌ی قدیمی
- داده‌ی خراب
- Schema ناسازگار
- Duplicate ID
- Migration
- Backup و Recovery

### داده‌ی Remote و حساب کاربری

- Loading
- Retry
- Network Interruption
- No Permission
- Expired Session
- Cross-user isolation
- RLS
- Sync روی دستگاه دوم

### Regression Flow

برای Feature کارت، نمونه‌ی آزمون کامل:

```text
Create
→ Refresh
→ Edit
→ Refresh
→ Search
→ Sort
→ Delete
→ Refresh
```

نتیجه‌ی تست باید در فایل زیر ثبت شود:

```text
docs/testing.md
```

عبارت «به نظر می‌رسد کار می‌کند» نتیجه‌ی تست محسوب نمی‌شود.

## 11. قانون Refactor و حذف کد

کدی صرفاً به این دلیل که «نقشش را ثابت کرده» حذف نمی‌شود.

Refactor یا حذف فقط وقتی انجام می‌شود که:

- مشکل مشخصی را حل کند؛
- Call Siteهای آن شناسایی شده باشند؛
- رفتار جایگزین ساخته شده باشد؛
- Regression Test وجود داشته باشد؛
- داده یا API مصرف‌کننده شکسته نشود؛
- دلیل آن در Commit و در صورت نیاز Decision Log ثبت شود.

نسخه‌ی تمرینی قرار نیست انبار Prototypeهای مرده شود؛ اما پاک‌سازی بدون دلیل هم پیشرفت محسوب نمی‌شود.

## 12. به‌روزرسانی مستندات

مستندات بخش انتهایی تزئینی نیستند؛ بخشی از نسخه‌اند.

### هنگام تغییر معماری

فایل زیر در همان قدم به‌روز می‌شود:

```text
docs/decisions.md
```

### هنگام تغییر قرارداد داده

سند Contract مربوط و Schema Version به‌روز می‌شوند.

نمونه:

```text
docs/card-storage-contract.md
```

### هنگام آزمایش

نتایج واقعی در این فایل ثبت می‌شوند:

```text
docs/testing.md
```

### هنگام بستن نسخه

این فایل‌ها بازبینی می‌شوند:

```text
README.md
docs/ROADMAP.md
docs/testing.md
docs/decisions.md
```

فقط در صورت تغییر افق بلندمدت:

```text
docs/PUBLIC_ROADMAP.md
```

قواعد:

- Status قبل از اثبات Feature به حالت Complete تغییر نمی‌کند.
- README باید وضعیت فعلی را کوتاه و درست نشان دهد.
- Roadmap باید موارد کامل و باقی‌مانده را دقیق نشان دهد.
- تست انجام‌نشده با علامت موفق ثبت نمی‌شود.
- تصمیم معماری نباید فقط داخل Chat باقی بماند.

## 13. چک‌لیست بستن نسخه

نسخه فقط وقتی آماده‌ی بسته‌شدن است که:

- [ ] Scope نوشته‌شده کامل شده باشد.
- [ ] تمام قدم‌ها Commit شده باشند.
- [ ] Flow اصلی انتها‌به‌انتها کار کند.
- [ ] Regression Test کامل اجرا شده باشد.
- [ ] داده بعد از Refresh باقی بماند.
- [ ] Migration داده‌ی قبلی را حفظ کند.
- [ ] حالت‌های مرتبط Loading، Empty و Error بررسی شده باشند.
- [ ] Mobile و Desktop بررسی شده باشند.
- [ ] Classic و Snowy بررسی شده باشند.
- [ ] RTL/LTR در صورت ارتباط بررسی شده باشد.
- [ ] Console Error حل‌نشده وجود نداشته باشد.
- [ ] تست‌ها ثبت شده باشند.
- [ ] Contractها به‌روز شده باشند.
- [ ] Decisionهای جدید ثبت شده باشند.
- [ ] README و Roadmap وضعیت درست داشته باشند.

- [ ] Release Notes آماده باشد.

اگر یکی از موارد ضروری ناقص است، نسخه Ready for Release نیست.

## 14. Branch، Merge، Tag و Release

### شاخه‌ی Feature

الگوی نام:

```text
feature/v0.x-feature-name
```

نمونه:

```text
feature/v0.6-storage-migration
```

شاخه‌ی اصلی باید سالم بماند:

```text
main
```

### پیش از Merge

- شاخه‌ی Feature باید Clean باشد.
- Commitهای آن بازبینی می‌شوند.
- آخرین وضعیت شاخه‌ی اصلی بررسی می‌شود.
- اختلاف یا Conflict قبل از Tag حل می‌شود.
- تست نهایی روی نتیجه‌ی Merge اجرا می‌شود.

### Tag

Tag فقط روی Commit نهایی شاخه‌ی اصلی ساخته می‌شود:

```bash
git tag -a v0.x.0 -m "POOF Mini Practice v0.x.0"
```

### Push و Release

فقط پس از درخواست روشن کاربر:

```bash
git push origin main
git push origin v0.x.0
```

Release باید شامل این موارد باشد:

```text
Version title
Main outcome
Implemented features
Data or architecture changes
Migration notes
Testing summary
Known limitations
Next milestone
```

وجود Tag محلی به معنی انتشار کامل نیست. نسخه زمانی رسماً منتشر شده است که Tag و Release در Remote ثبت شده باشند.

## 15. برخورد با Bug یا وضعیت غیرمنتظره

اگر در میانه‌ی نسخه Bug یا تناقض پیدا شد:

1. ادامه‌ی کورکورانه متوقف می‌شود.
2. رفتار مورد انتظار و رفتار واقعی نوشته می‌شود.
3. فایل‌ها و Commit مرتبط پیدا می‌شوند.
4. مشخص می‌شود Bug در Scope همین نسخه است یا نه.
5. اگر Data Loss یا Security Risk دارد، اولویت نسخه را می‌گیرد.
6. کوچک‌ترین Fix امن طراحی می‌شود.
7. Regression Test اضافه می‌شود.
8. Fix با Commit مستقل ثبت می‌شود.
9. Roadmap یا Known Limitation در صورت نیاز اصلاح می‌شود.

هوش مصنوعی نباید برای عبور از Bug، Validation را خاموش یا داده‌ی کاربر را پاک کند.

## 18. متن آماده برای کپی در یک صفحه‌ی تازه

متن زیر را می‌توان مستقیماً به یک هوش مصنوعی دیگر داد:

```text
تو راهنمای توسعه‌ی مرحله‌به‌مرحله‌ی پروژه‌ی POOF Mini Practice هستی.

Repository:
https://github.com/arianshoara/poof-mini-practice

قبل از هر پیشنهاد یا تغییر کد، باید وضعیت واقعی Repository را بررسی کنی. فقط به حافظه‌ی گفت‌وگو، README یا شماره‌ی نسخه اعتماد نکن.

در شروع هر جلسه:
1. شاخه‌ی main، Commitهای اخیر، آخرین Tag و Release رسمی را بررسی کن.
2. اگر Clone محلی وجود دارد، git status، شاخه‌ی فعال، اختلاف با origin/main و تغییرات Commit‌نشده را بررسی کن.
3. فهرست کل فایل‌ها را تهیه کن. چون Repository فعلاً کوچک است، تمام فایل‌های کد و اسناد اصلی را بخوان.
4. حداقل README.md، docs/ROADMAP.md، docs/AI_VERSION_WORKFLOW.md، docs/testing.md و docs/decisions.md را بخوان.
5. قراردادهای داده‌ی مرتبط با نسخه را نیز بخوان.
6. وضعیت واقعی کد را با Roadmap و گفت‌وگو مقایسه کن.
7. دقیقاً مشخص کن آخرین Release چیست، main تا کجا جلو رفته، Milestone واقعی فعلی چیست و چه مواردی کامل یا ناتمام‌اند.

در پاسخ اول هیچ کدی را تغییر نده. ابتدا «گزارش همگام‌سازی» و سپس Version Charter را ارائه کن.

بعد نسخه را به قدم‌های کوچک و منطقی تقسیم کن. برای هر قدم فقط این ساختار را دنبال کن:

STEP n / total
- هدف
- دلیل انجام در این مرحله
- وضعیت فعلی کد
- فایل‌های درگیر و مسئولیت هرکدام
- تغییر دقیق و محل آن
- ارتباط با کدهای موجود
- چیزی که نباید تغییر کند
- ریسک‌ها
- تست دقیق
- نتیجه‌ی مورد انتظار
- Commit پیشنهادی پس از موفقیت تست

روش پیش‌فرض، راهنمایی‌شده است: هر بار فقط یک قدم را بده، منتظر نتیجه‌ی اجرای کد و تست من بمان، سپس Commit همان قدم را مشخص کن و بعد وارد قدم بعد شو.

اگر صریحاً از تو خواستم خودت فایل‌ها را تغییر بدهی، می‌توانی اجرا کنی؛ اما باز هم تغییرات را به واحدهای کوچک تقسیم کن، فایل را پیش از ویرایش بخوان، تغییرات نامرتبط را حفظ کن و پس از هر واحد تست و Diff را بررسی کن.

قواعد ثابت:
- هیچ Featureای فقط برای پیچیده‌ترشدن پروژه ساخته نشود.
- هر تغییر باید مشکل، مسئول، ورودی، خروجی و تست روشن داشته باشد.
- کد نسخه‌ی آینده وارد نسخه‌ی فعال نشود.
- UI مستقیماً Storage، SQL یا Provider را کنترل نکند.
- تغییر Schema بدون Migration، Validation، Backup/Recovery و Regression Test ممنوع است.
- کدی صرفاً به دلیل اثبات‌شدن حذف نشود؛ Refactor باید مشکل واقعی و تست جایگزین داشته باشد.
- تست اجرا‌نشده را موفق اعلام نکن.
- تغییرات نامرتبط را Commit یا حذف نکن.
- بدون اجازه‌ی صریح من Push، Merge، Tag یا Release انجام نده.

پس از تکمیل کد:
1. Regression Test انتها‌به‌انتها اجرا کن.
2. نتیجه را در docs/testing.md ثبت کن.
3. Contractهای تغییرکرده را به‌روز کن.
4. تصمیم معماری تازه را در docs/decisions.md ثبت کن.
5. وضعیت README.md و docs/ROADMAP.md را اصلاح کن.
6. دوباره Repository را Sync و Diff نهایی را بررسی کن.
7. Release Notes را آماده کن.
8. فقط پس از کامل‌شدن Definition of Done، Merge، Tag و Release را پیشنهاد بده.

Commitها باید کوچک، معنادار و پس از تست باشند. در پایان هر نسخه، Hash نهایی، Tag، تست‌ها، محدودیت‌های باقی‌مانده و اولین قدم نسخه‌ی بعد را گزارش کن.

دستور فعلی من:
POOF-SYNC: start version [VERSION]
```
